[[section-runtime-view]]
== Vista en Tiempo de Ejecución

Esta sección describe cómo se comportan los componentes del sistema durante la ejecución, mostrando los flujos más relevantes mediante diagramas de secuencia.

=== Escenario 1: Registro e inicio de sesión

El usuario accede a la aplicación e introduce sus credenciales. El servicio `users` valida los datos y devuelve un token de sesión.

[plantuml, runtime-login, png]
----
@startuml
actor Usuario
participant "webapp" as web
participant "users" as users
database "MongoDB" as mongo

Usuario -> web: Introduce credenciales
web -> users: POST /login
users -> mongo: Consulta usuario
mongo --> users: Datos del usuario
users --> web: Token de sesión
web --> Usuario: Redirige al lobby
@enduml
----

=== Escenario 2: Inicio de partida

El usuario configura una nueva partida eligiendo tamaño del tablero, tipo de oponente y, si es bot, estrategia y nivel.

[plantuml, runtime-newgame, png]
----
@startuml
actor Usuario
participant "webapp" as web
participant "gamey" as gamey

Usuario -> web: Configura partida (tamaño, oponente, estrategia)
web -> gamey: POST /game/new
gamey --> web: Estado inicial del tablero en YEN
web --> Usuario: Muestra tablero
@enduml
----

=== Escenario 3: Turno de juego contra el bot

El usuario hace clic en una celda. El frontend envía el movimiento al motor de juego, que lo valida, comprueba si hay ganador y calcula la respuesta del bot.

Hacer diagrama
----
@startuml
actor Usuario
participant "webapp" as web
participant "gamey" as game

Usuario -> web: Hace un movimiento
web -> game: POST /game/:gameId/move
game --> web: YEN con la respuestadel bot
web --> Usuario: Muestra el nuevo estado del tablero
@enduml
----

=== Escenario 4: Fin de partida

Cuando el motor detecta un ganador, se notifica al frontend y la partida queda registrada en el historial.

[plantuml, runtime-endgame, png]
----
@startuml
actor Usuario
participant "webapp" as web
participant "gamey" as gamey
participant "users" as users
database "MongoDB" as mongo

gamey --> web: Victoria/derrota detectada
web -> users: POST /savegame (resultado de la partida)
users -> mongo: Guarda partida
mongo --> users: OK
web --> Usuario: Muestra resultado final
@enduml
----

=== Escenario 5: Consulta del historial

El usuario accede a su historial de partidas desde el lobby.

[plantuml, runtime-history, png]
----
@startuml
actor Usuario
participant "webapp" as web
participant "users" as users
database "MongoDB" as mongo

Usuario -> web: Accede al historial
web -> users: GET /history/:userId
users -> mongo: Consulta partidas del usuario
mongo --> users: Lista de partidas
users --> web: Estadísticas e historial
web --> Usuario: Muestra historial
@enduml
----

=== Escenario 6: Consulta de historial con filtrado
El usuario accede a su perfil y solicita ver sus partidas pasadas. El sistema permite filtrar por rival, resultado o fecha para optimizar la visualización.

[plantuml, runtime-history, png]
----
@startuml
actor Usuario
participant "webapp" as web
participant "users-service" as users
database "MongoDB" as mongo

Usuario -> web: Accede a Historial
web -> users: GET /history/{username} (filters)
users -> mongo: find(GameRecord) con criterios
mongo --> users: Lista de partidas
users --> web: JSON (GameHistoryRecord[])
web --> Usuario: Renderiza tabla filtrada
@enduml
----

[role="arc42help"]
****
.Contents
The runtime view describes concrete behavior and interactions of the system’s building blocks in form of scenarios from the following areas:

* important use cases or features: how do building blocks execute them?
* interactions at critical external interfaces: how do building blocks cooperate with users and neighboring systems?
* operation and administration: launch, start-up, stop
* error and exception scenarios

Remark: The main criterion for the choice of possible scenarios (sequences, workflows) is their *architectural relevance*. It is *not* important to describe a large number of scenarios. You should rather document a representative selection.

.Motivation
You should understand how (instances of) building blocks of your system perform their job and communicate at runtime.
You will mainly capture scenarios in your documentation to communicate your architecture to stakeholders that are less willing or able to read and understand the static models (building block view, deployment view).

.Form
There are many notations for describing scenarios, e.g.

* numbered list of steps (in natural language)
* activity diagrams or flow charts
* sequence diagrams
* BPMN or EPCs (event process chains)
* state machines
* ...


.Further Information

See https://docs.arc42.org/section-6/[Runtime View] in the arc42 documentation.
