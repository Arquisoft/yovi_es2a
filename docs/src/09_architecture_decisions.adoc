=== Introducción

En esta sección documentamos las decisiones arquitectónicas significativas que darán forma a la estructura, el despliegue y la tecnología del sistema YOVI. Estas decisiones se tomarán considerando los requisitos no funcionales, las restricciones del proyecto y la experiencia del equipo de desarrollo.

El objetivo de este registro es proporcionar trazabilidad y justificación sobre por qué se eligieron ciertas soluciones frente a otras alternativas disponibles, utilizando el formato de registros de decisión (ADR).

=== ADR-001: Uso de MongoDB como base de datos

* **Estatus:** Aceptado.

* **Contexto:** Se necesitaba persistir información de usuarios y su historial de partidas.

* **Decisión:** Se utilizará **MongoDB** como base de datos, en lugar de una base de datos relacional como PostgreSQL o MySQL.

* **Justificación:**
Consideramos una mejor decisión el uso de una base de datos NoSQL como MongoDB debido a la simplicidad del modelo de datos y la ausencia de relaciones complejas. MongoDB permite almacenar documentos JSON, lo que simplifica mucho la gestión de la información de los usuarios y su historial de partidas sin necesidad de diseñar esquemas rígidos o realizar migraciones frecuentes.
+
De hecho, gracias a la flexibilidad en el esquema que proporciona Mongo, pudimos despreocuparnos en gran medida de la información relacionada con el historial y las estadísticas de cada usuario, lo que nos permitió centrarnos e ir poco a poco con el proyecto.
+
Por último, la integración con el microservicio de usuarios en Node.js es directa mediante Mongoose, lo que facilita el desarrollo y mantenimiento del sistema. Por no hablar de que los miembros del equipo ya teníamos cierta experiencia con bases de datos no relacionales y consideramos interesante practicar el uso de MongoDB.

* **Alternativas consideradas:** PostgreSQL / MySQL -> Descartadas por añadir complejidad innecesaria (esquemas rígidos, migraciones) para un modelo de datos tan simple. 

* **Consecuencias:**
** El esquema es flexible y fácil de extender.
** No se dispone de validación de integridad referencial a nivel de base de datos, aunque no resulta especialmente relevante dada nuestra estructura de datos.
** La integración con el microservicio de usuarios en Node.js es directa mediante Mongoose.

=== ADR-002: Estrategia de filtrado en el historial de partidas

* **Estatus:** Aceptado.
* **Contexto:** El usuario necesita consultar miles de registros. Realizar peticiones por cada pulsación de tecla (live search) saturaría el servicio de usuarios.
* **Decisión:** Se implementa un estado temporal en el Frontend para el input de "Rival" y una ejecución "Lazy" de la búsqueda. La petición a la API solo se dispara al pulsar el botón "Buscar".
* **Consecuencias:** Mejora del rendimiento de red y reducción de carga en MongoDB.

=== ADR-003: Argon2id como algoritmo de hashing de contraseñas

* **Estatus:** Aceptado.

* **Contexto:** El sistema necesita almacenar contraseñas de usuarios de forma 
segura en MongoDB. Era necesario elegir un algoritmo de hashing que protegiera 
las credenciales ante posibles filtraciones de la base de datos.

* **Decisión:** Se utiliza **Argon2id** mediante la librería `argon2` de Node.js para hashear las contraseñas antes de persistirlas y para verificarlas en el login.

* **Justificación:** Investigando un poco descubrimos que Argon2id es actualmente la recomendación del OWASP (Open Web Application Security Project) para el almacenamiento seguro de contraseñas. A diferencia de alternativas como bcrypt o SHA-256, Argon2id está diseñado para ser resistente tanto a ataques de fuerza bruta por GPU como a ataques de canal lateral, gracias a su configuración de coste de memoria y tiempo. Su variante `id` combina las ventajas de Argon2i (resistencia a side-channel) y Argon2d (resistencia a GPU), siendo la opción más equilibrada y segura.

[NOTE]
Los ataques de canal lateral son técnicas de ciberseguridad que obtienen información confidencial (como claves criptográficas) analizando características físicas indirectas de un sistema —consumo de energía, tiempo de ejecución, emisiones electromagnéticas o sonido— en lugar de explotar vulnerabilidades en el código.

* **Alternativas consideradas:**
** _bcrypt_ → Válido y ampliamente usado, pero más antiguo y menos resistente a 
hardware moderno de ataque paralelo.
** _SHA-256 / SHA-512_ → Descartados. Son algoritmos de propósito general, no 
diseñados para contraseñas, y son vulnerables a ataques de fuerza bruta por su 
velocidad de cómputo.

* **Consecuencias:**
** Las contraseñas nunca se almacenan en texto plano ni con hashes reversibles.
** El proceso de login introduce una latencia mínima pero aceptable por el coste 
computacional del algoritmo, lo que es precisamente una de sus propiedades de seguridad. Esto retrasa un poco los tiempos de respuesta, pero no lo suficiente como para afectar negativamente la experiencia del usuario ni al rendimiento general de la aplicación.
** Ante una filtración de la base de datos, los hashes son computacionalmente 
inviables de revertir en un tiempo razonable.

=== ADR-004: Identificación de usuario mediante localStorage y header X-User

* **Estatus:** Aceptado.

* **Decisión:**
Se implementa un mecanismo de identificación de usuario en cliente, basado en el almacenamiento del identificador (`_id`) en `localStorage`, el cual se envía en cada petición HTTP mediante el header personalizado `X-User`.

Este mecanismo no constituye un sistema de autenticación, sino únicamente una forma de identificar al usuario en sistemas de baja criticidad.

* **Justificación:**
El flujo funciona de la siguiente manera: tras un login exitoso, el microservicio de usuarios devuelve el `_id` (identificador único en MongoDB). Este valor se almacena en el `localStorage` del navegador bajo la clave `userId`. En las peticiones posteriores que requieren identificación (como consultar historial, perfil o ranking), el frontend incluye este valor en el header `X-User`.

La decisión se basa en priorizar la simplicidad de implementación, reduciendo la complejidad tanto en cliente como en servidor. No se requiere gestión de tokens (firma, expiración, refresh) ni almacenamiento de sesiones.

El backend utiliza este identificador para recuperar la información del usuario desde la base de datos.

Se asume explícitamente que el cliente es responsable de enviar el identificador y que el servidor no valida su autenticidad.

* **Alternativas consideradas:**
** JWT (JSON Web Token) → Descartado por añadir complejidad (firma, expiración, validación), aunque proporciona autenticación verificable y mayor seguridad.
** Cookies con HttpOnly + sesión → Descartado por requerir estado en el servidor y configuración adicional (protección CSRF, gestión de cookies seguras).

* **Consecuencias:**
** Ventajas:
*** Implementación simple y rápida.
*** Bajo acoplamiento entre cliente y servidor.
*** No requiere gestión de sesiones ni tokens.

** Limitaciones y riesgos:
*** No existe autenticación real: el servidor confía en el valor recibido.
*** Posible suplantación de identidad enviando un `X-User` arbitrario.
*** No hay expiración automática de sesión.
*** Requiere validación de existencia del usuario en cada petición.

=== ADR-005: Fórmula de puntuación ponderada para el ranking global

* **Estatus:** Aceptado.

* **Contexto:** Al añadir el ranking global se necesitaba una métrica de ordenación justa. Las alternativas triviales (victorias totales, ratio de victorias) tienen sesgos bien conocidos: la primera ignora la dificultad del rival, la segunda infla a jugadores con muy pocas partidas.

* **Decisión:** Se utiliza la siguiente fórmula, calculada en tiempo real en `GET /ranking` agregando la colección `GameRecords`:

[source]
----
Score(j) = Σ d(i) · V_i · C(N_i) · (1 + V_i/N_i)
donde:
  d(i)          = peso de dificultad del rival i
  V_i           = victorias contra el rival i  [factor dominante]
  C(N)          = 1 − exp(−N / K)             [confianza estadística, K=10: ~30 partidas para confianza plena]
  (1 + V_i/N_i) = bonus de eficacia ∈ (1,2]  [α=1.0: bonus significativo pero no principal]
----

Los pesos de dificultad asignados son:

[cols="2,1", options="header"]
|===
| Rival | d(i)
| random_bot | 1.0
| offensive_easy / defensive_easy / positional_easy | 1.5
| offensive_medium / defensive_medium / positional_medium | 2.5
| offensive_hard / defensive_hard / positional_hard | 4.0
| Jugador humano | 5.0
| monte_carlo_bot | 7.0
|===

* **Desglose matemático de los factores:**

** **`d(i)` — Peso de dificultad:** escala la contribución de cada rival según su complejidad algorítmica. Va de 1.0 (random_bot) a 7.0 (monte_carlo_bot). Los jugadores humanos reciben 5.0 por su imprevisibilidad.

** **`V_i` — Victorias absolutas (factor dominante):** usar las victorias en bruto en lugar del ratio `V/N` hace que jugar más partidas siempre aporte puntos positivos. Premia la actividad sostenida, no solo la eficacia puntual.

** **`C(N) = 1 − exp(−N/10)` — Factor de confianza estadística:** función creciente que satura hacia 1 conforme crece la muestra. Con 1 partida `C ≈ 0.10`, con 10 partidas `C ≈ 0.63`, con 30 partidas `C ≈ 0.95`. Evita que una única victoria infle artificialmente la puntuación.

** **`(1 + V_i/N_i)` — Bonus de eficacia (α = 1.0):** término multiplicativo ∈ (1, 2] que añade hasta un 100 % extra cuando el jugador gana todas las partidas contra ese rival (`V/N = 1 → factor = 2`). Si no gana ninguna (`V/N = 0 → factor = 1`) no penaliza, simplemente no bonifica. Es un bonus significativo pero nunca el factor principal.

+
A modo de ejemplo numérico, un jugador con 5 victorias en 10 partidas contra `monte_carlo_bot` (d = 7.0) obtiene:
+
[source]
----
C(10)        = 1 − exp(−10/10)  ≈ 0.632
bonus        = 1 + 5/10          = 1.5
aporte       = 7.0 · 5 · 0.632 · 1.5  ≈ 33.18 puntos
----

* **Alternativas consideradas:**
** _Victorias totales_ → Descartada. Ignora la dificultad del rival.
** _Ratio puro V/N_ → Descartada. Una sola victoria da ratio 100 %, inflando el ranking con muestras mínimas.
** _ELO_ → Descartada. Requiere estado persistente adicional y lógica de actualización bidireccional tras cada partida, añadiendo complejidad sin ventaja real dado el volumen de datos del sistema.

* **Consecuencias:**
** El ranking premia simultáneamente actividad (victorias absolutas), calidad (bonus de eficacia) y rigor estadístico (confianza).
** El cálculo en tiempo real puede degradarse con un volumen muy elevado de `GameRecords`. Mitigable con un índice MongoDB sobre `username`.
** Incorporar un nuevo bot requiere únicamente asignarle un peso en `RIVAL_WEIGHTS` del servicio `users`.

=== ADR-006: Ausencia de Gateway — Acceso directo a microservicios

* **Estatus:** Aceptado.

* **Contexto:** En una arquitectura de microservicios, como vimos más tarde en clase, es habitual centralizar el tráfico entrante a través de un gateway que actúe como punto único de entrada. Para el momento de tomar esta decisión teníamos que definir el cómo hacer la API pública para los bots externos.

* **Decisión:** Se descarta el uso de un gateway centralizado. En su lugar:
** La **webapp** (React) accede directamente a `users` para hacer las operaciones relacionadas con la gestión de usuarios y directamente a `gamey` para la lógica del juego.
** Los **bots externos** acceden directamente al motor de juego mediante 
`GET /play` en notación YEN, sin intermediario.

* **Justificación:** Consideramos que añadir una gateway sería complicar la arquitectura de forma innecesaria en vista de la poca cantidad de endpoints disponibles y la simplicidad de estos. Además, en vista de que nuestra aplicación no está diseñada para manejar un amplio tráfico de bots externos o usuarios, resolvimos tomar la opción más sencilla de implementar.

* **Alternativas consideradas:**
** _nginx como reverse proxy_ → Descartado. Añade configuración adicional sin aportar valor real dado que no hay colisión de puertos ni necesidad de balanceo de carga con el volumen actual.
** _Gateway Node.js propio_ → Descartado. Requeriría desarrollo y mantenimiento de una capa extra que duplicaría lógica ya presente en la webapp.

* **Consecuencias:**
** La arquitectura es más simple y fácil de desplegar y depurar.
** La webapp asume la responsabilidad de seleccionar el servicio correcto en cada operación, acoplando ligeramente el frontend a la topología de servicios.
** Si en el futuro se añaden más microservicios o se requiere autenticación centralizada, la introducción de un gateway sería la evolución natural del sistema que resultaría sencilla de implementar.

=== ADR-007: Política de Saneamiento Estricto (Allowlist) en la Comunicación

* **Estatus:** Aceptado.

* **Contexto:** Durante el análisis de código estático con SonarCloud, se identificaron vulnerabilidades críticas de seguridad. Estas ocurrían al inyectar parámetros del usuario directamente en las rutas de las peticiones HTTP (fetch).

* **Decisión:** Se rechaza el uso de comentarios de evasión (// NOSONAR) o listas de bloqueo de caracteres. En su lugar, se implementa una política de Validación por Lista Blanca (Allowlist).

* **Justificación:** Se ha centralizado la seguridad en una función (sanitizeParam) que utiliza una expresión regular estricta (^[a-zA-Z0-9_-]+$). Esto asegura matemáticamente que cualquier dato que viaje hacia los microservicios sea inofensivo, bloqueando la petición en el cliente si se detectan caracteres de inyección (/, . o scripts). 

* **Alternativas consideradas:**
** // NOSONAR: Descartado por ser un antipatrón que oculta riesgos reales.

* **Consecuencias:**
** Mitigación efectiva de ataques de inyección en la URL.
** Cumplimiento estricto de los estándares de seguridad de SonarCloud.
** Ligera pérdida de flexibilidad en los nombres de usuario permitidos (restringidos a caracteres alfanuméricos y guiones).

=== ADR-008: Sistema de Amigos y Grupos

* **Estatus:** Aceptado.

* **Contexto:** Se decide añadir sistema YOVI un componente social básico que permitiera a los jugadores identificar a otros usuarios como amigos y participar en grupos para organizar partidas privadas.

* **Decisión:** Se implementa un sistema de relaciones sociales con las siguientes características:

**Amigos — Relación directa sin solicitud:**
* `POST /addfriend/:friendUsername`: Añade directamente al usuario especificado como amigo, sin mecanismo de solicitud/aceptación. La relación se almacena en la colección `Friend` con documentos `{ from, to }`.
* `DELETE /removefriend/:friendUsername`: Elimina la relación de amistad.
* `GET /friends/:username`: Devuelve la lista de amigos del usuario junto con sus estadísticas (partidas jugadas, victorias, ratio de victoria).

**Grupos — Un usuario, un grupo:**
* `POST /creategroup`: Crea un nuevo grupo público. El creador se añade automáticamente como admin y abandona cualquier grupo anterior al que pertenezca.
* `POST /joingroup/:groupId`: Un usuario se une a un grupo público. **Restricción:** un usuario solo puede pertenecer a un grupo a la vez.
* `GET /group/:groupId`: Devuelve los detalles del grupo y la lista de miembros con sus roles.

* **Justificación:**
La decisión de implementar amigos y grupos como relaciones directas (sin solicitudes ni invitaciones) responde a la prioridad de simplicidad del proyecto. No se consideró necesario un flujo de solicitud-aceptación para amigos ni un sistema de invitaciones para grupos en esta versión.

La restricción de "un usuario, un grupo" simplifica la lógica de pertenencia y evita la complejidad de gestionar múltiples grupos por usuario.

* **Alternativas consideradas:**
** Solicitudes de amistad → Descartado para esta versión. Añadiría estados (pendiente, aceptado, rechazado) y notificaciones.

* **Consecuencias:**
** La consulta de amigos es simple: búsqueda en la colección `Friend` por `from`.
** Un usuario puede ver sus amigos y sus estadísticas desde el frontend.
** Un usuario puede abandonar su grupo actual uniéndose a otro, o creando uno nuevo.
** No hay sistema de chat integrado dentro de grupos.
** No hay posibilidad de expulsar miembros ni de transferir el rol de admin.
